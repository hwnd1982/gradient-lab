# Agent API (dev + прод на Vercel)

HTTP API для ИИ-агентов: можно читать текущее состояние блока, менять его live (браузер обновляется мгновенно), забирать JSON-схему стейта, diff-анализ против макета с выбором таргета, предупреждения борт-контроля и управлять пресетами. Живёт в двух режимах: **dev** — Vite-middleware dev-сервера (`npm run dev`, порт 5180, обновления браузеру по SSE) и **прод** — функции Vercel `api/*.js` (генерат из `server/functions/*.ts`, см. «Прод (Vercel)») со стором Upstash Redis (обновления браузеру поллингом версий; раздел «[Прод (Vercel)](#прод-vercel)» ниже). Контракт данных/форматы ответов в обоих режимах совпадают.

Схема работы: **агент делает `PUT /api/state` → открытые браузеры получают стейт (dev — по SSE мгновенно, прод — поллингом ~10 с) и обновляются live**. В обратную сторону браузер сам шлёт свой текущий стейт (debounce 300ms) через `POST /api/__sync` (на проде — `POST /api/sync`), diff-анализ (debounce ~500ms) — через `POST /api/__analysis`, предупреждения борт-контроля (debounce ~400ms) — через `POST /api/__warnings`, журнал итераций (debounce ~700ms на устоявшееся изменение) — через `POST /api/__journal` (читайте его как `GET /api/journal`). Подбор ведётся по методике v2: алгоритм — `GET /api/methodology`, «движение к точке» — поле `hint` анализа, коридор радиуса одной командой — `POST /api/sweep`.

Гонка обратного синка закрыта: после агентского `PUT` эхо браузера **не перетирает поля** (в dev стейт, применённый из SSE, не уходит обратно в `/api/__sync`; на проде эхо разрулено по версиям — см. «Контракт версий» в разделе «Прод (Vercel)»); юзерские правки поверх применённого — нормальный last-writer-wins. Контроль — сверка `GET /api/state` через ~2 с после PUT (на проде — с учётом поллинга ~10 с, сверяйте через ~12 с).

Зум/пан стейджа в UI (Ctrl+колесо — зум к курсору 10..800%; пан — drag пустого места, Space/СКМ; Alt+drag пустого — фон стейджа; кнопки Fit/50/100/200/300 и степпер −/+) — **view-only**: живёт только в сессии браузера, не входит в `BlockState`, не синкается в API и не участвует в координатах анализа — анализ всегда считается в системе блока. Старт, пресеты и share-ссылки открываются в режиме Fit; агентский `PUT /api/state` вид не трогает.

Все эндпоинты — валидация через zod-схему `BlockStateSchema` (см. `src/schema.ts`).

## Состояние блока

### `GET /api/state` — текущий стейт

Последний засинканный стейт (от браузера или от агента). `404`, пока ничего не синкалось.

```bash
curl http://localhost:5180/api/state
```

### `PUT /api/state` — положить стейт (live-обновление браузера)

Тело — полный `BlockState` (проверяется zod-схемой). При невалидном теле — `400` с массивом `issues`. Успех кэширует стейт и броадкастит его всем SSE-клиентам.

```bash
curl -X PUT http://localhost:5180/api/state \
  -H 'Content-Type: application/json' \
  -d @state.json
# {"ok":true}
```

### `POST /api/__sync` — браузер шлёт свой стейт (на проде — `POST /api/sync`)

Вызывается самим приложением (debounce 300ms после любой правки). Кэширует стейт, но НЕ броадкастит. Агенту обычно не нужен.

### `POST /api/__analysis` — браузер шлёт diff-анализ (на проде — `POST /api/analysis`)

Вызывается самим приложением (debounce ~500ms) при загруженном `compare.refImage`. Кэширует результат как «последний анализ» вместе с его `target`; тело `{"cleared":true}` (референс убрали) сбрасывает кэш. Агенту обычно не нужен.

### `GET /api/analysis?target=<key>` — последний diff-анализ против референса

Perfect Pixel-метрики для решения «что двигать». Без `?target` — последний анализ, посчитанный приложением (для активного в UI таргета или последнего агентского запроса). С `?target=<key>` — анализ конкретного таргета:

- `base`, `blockMask` (маска блока; алиас `mask`), `blurMask`, `blurBg`, `underlay`, `clipText`, `animFrom`, `animTo`, `layer:<index>` (напр. `layer:0`). Числовой индекс нормализуется: `layer:007` → канонический `layer:7` — ответ всегда под каноническим ключом.
- Если кэш уже считался для этого же таргета — сразу `200` с анализом. Иначе в dev сервер броадкастит приложению SSE-событие `{"type":"analysis-request","target":...}` (приложение переключает таргет анализа и пересчитывает), а на проде заявку пишет в очередь (браузер забирает её поллингом версий ~10 с и пересчитывает). Ответ в обоих случаях — `404` с `{"error":"...","requested":"<key>"}` — **поллите тот же GET раз в ~1 с (прод: ~3 с), пока не придёт `200` c `"target": "<key>"` в теле** (на проде — в течение ~12 с). Требуется открытая вкладка приложения (кэш живёт, пока вкладка шлёт POST).
- Невалидный таргет — `400` со списком `known` (полный список всех валидных ключей; единый источник — `KNOWN_TARGET_KEYS` в `shared/targetKeys.ts`, этот список держать синхронным).
- `200` может прийти **маркером вместо анализа**: `{"target":"...","gradientMissing":true}` — у таргета нет градиента (слой за диапазоном, `blurMask` без маски, плоский цвет у `blurBg`/`underlay`); `{"target":"...","blocked":"no-reference"}` — референс не загружен (`compare.refImage === null`). Маркер = «чини старт, не крути стопы»: создай градиент (`PUT /api/state`) или попроси юзера загрузить референс; поллинг 404 больше не нужен.

Схема — `AnalysisSchema` в `src/schema.ts`. `404` до первого анализа: загрузите референс в приложении.

```bash
curl http://localhost:5180/api/analysis?target=blurMask
```

Пример ответа:

```json
{
    "matchPercent": 87.3,
    "zoneMatchPercent": 94.6,
    "maxError": 142,
    "tolerance": 10,
    "target": "blurMask",
    "profile": "axis",
    "axisSpace": "blur.rect",
    "zone": { "x": 0, "y": 68.75, "w": 100, "h": 31.25 },
    "axis": [
        { "pos": 0, "ref": [16, 16, 16, 255], "got": [26, 26, 26, 255], "err": 6.5 },
        { "pos": 45.1, "ref": [16, 16, 16, 24], "got": [16, 16, 16, 190], "err": 83 }
    ],
    "transitions": [
        { "pos": 40.5, "level": 220 },
        { "pos": 74.6, "level": 18 }
    ],
    "suggestedStops": [
        { "pos": 0, "alpha": 0.86 },
        { "pos": 40.5, "alpha": 0.86 },
        { "pos": 74.6, "alpha": 0.07 },
        { "pos": 100, "alpha": 0.07 }
    ],
    "residuals": [
        { "pos": 45.1, "err": 83, "kind": "level" },
        { "pos": 2.4, "err": 71, "kind": "edge" },
        { "pos": 60, "err": 44, "kind": "blur" }
    ],
    "verdict": "остатки уровня: примените suggestedStops (топ-10: кромки 2, blur 3, уровень 5)",
    "hint": "Примени suggestedStops к blurMask (F4)",
    "updatedAt": 1760000000000

```

Трактовка:

- `target` — таргет, для которого считался анализ (ключ из списка выше). Сверяйте с запрошенным: пока не совпал — это чужой/старый анализ. Маркер вместо анализа (`gradientMissing`/`blocked`) — см. выше.
- `profile` — режим профиля: `"axis"` — вдоль оси градиента таргета; `"columns"` — колонковый (галка «Профиль по колонкам»): ступени/стопы считаются по P60 яркости вертикальных колонок по оси X, в пространстве `axisSpace` (для rect-таргетов — 0..100 их rect, стопы применяются к градиенту элемента как есть); `"rays"` — по лучам (галка «По лучам», только radial-таргеты): 16 лучей из центра градиента до ending-shape, на каждом нормированном радиусе — медиана поканально; позиции честно радиусные (% радиуса в axisSpace). Ось-линия слепа к объектам вне линии, лучи видят всю зону.
- `axisSpace` — пространство координат оси: `"block"` (проценты вдоль оси всего блока) или `"blur.rect"` / `"underlay.rect"` / `"layer.rect"` (проценты вдоль оси rect-области — градиент элемента в CSS считается от его border-box; для `layer:N` с неполным rect ось живёт в системе rect слоя, полный rect = `"block"`). `zone` — зона эффекта в % ОТ блока (для blur-таргетов — `blur.rect`, для underlay — его rect, для слоя с неполным rect — rect слоя, иначе весь блок).
- `matchPercent` — % пикселей блока с расхождением < `tolerance` (пиксель считается по r,g,b,a вместе). Главная метрика «уже похоже/не похоже».
- `zoneMatchPercent` — то же, но только внутри `zone`: честная метрика качества фейда там, где он есть (глобальный процент размазывается по всему блоку).
- `maxError` — максимальное расхождение (0..255).
- `axis` — профиль вдоль оси таргета (64 точки): `ref` — референс, `got` — текущий блок, `err` — расхождение.
- `transitions` — «ступени» референса: где вдоль оси уровень меняется резко (уровень = альфа для PNG с прозрачностью, иначе luminance). Это границы, которые надо ловить стопами.
- `suggestedStops` — стопы по ступеням и краям: `alpha` для альфа-таргетов (маска блока, `blurMask`, `blurBg`, `underlay` — все фейды по природе), `color` для цветовых. В UI есть кнопка «Применить предложенные стопы».
- `residuals` — значимые остатки (`err > tolerance`) с классификацией: `edge` — кромка оси или граница rect-зоны (альфой не лечится, правь геометрию), `blur` — внутри blur-зоны (крутите радиус/стопы маски), `level` — уровень (лечится стопами), `approx` — колонковый профиль (`profile: "columns"`): позиции residual живут вдоль оси градиента, а ступени — по X, поэтому классификация приблизительна — сверяйтесь со `transitions` и heat-картой.
- `verdict` — человеческая сводка по топ-10 остатков: с чего начинать правку.
- `hint` (опционально, с недавних версий) — «движение к точке» по методике v2: готовый следующий шаг по фактам анализа + хвоста журнала. Правила (по приоритету): 1) последние ≥3 записи журнала крутили `blur.radius`, во всех известны дельты `zoneMatch` (before/after) и все < 0.5 → «Радиус на плато (F2 exit) — переходи к форме маски (F3): предразогрев 0.1@35% → фронт 0.5→1»; 2) verdict классифицирует остатки как кромки → «Остатки кромочные — альфа не поможет; проверь blur.rect/кадры (F1) или стоп»; 3) как уровень → «Примени suggestedStops к \<target\> (F4)»; 4) все остатки `kind='blur'` → «Крути blur.radius и форму blur.mask»; 5) иначе «Продолжай фазу; см. /api/methodology». Это подсказка перехода фазы, а не приказ: фазу держит агент (полная процедура — `GET /api/methodology`); в UI строка показывается внизу панели анализа.
- Приближения: backdrop-filter ЭМУЛИРУЕТСЯ (подстилающее содержимое блока блюрится внутри `blur.rect` через canvas `filter: blur()`; настоящий CSS блюрит и стейдж ЗА блоком). При `stage.isolated: true` за краем блока блюр сэмплит копии краевых пикселей (clamp-to-edge, как backdrop root с `isolation: isolate`), при `false` — прозрачность, край может быть темнее. Маска blur-слоя применяется к элементу целиком: вклад backdrop-эффекта пропорционален локальной альфе маски (промежуточные стопы маски меняют `got`/`zoneMatchPercent`). border-radius не клипует (дифф по прямому прямоугольнику); clip-text в дифф не рендерится.

### `POST /api/__warnings` — браузер шлёт предупреждения (на проде — `POST /api/warnings`)

Вызывается самим приложением (debounce ~400ms после правок). Кэширует payload; `{"cleared":true}` (предупреждений нет) сбрасывает кэш, чтобы агент никогда не получал устаревший список. Агенту обычно не нужен.

### `GET /api/warnings` — борт-контроль старта

Предупреждения о типовых ошибках подбора, которые приложение считает само: аспекты картинок, трансформ референса, покрытие переходов зоной blur, дубли стопов, нулевой радиус. Проверяйте ПОСЛЕ каждого PUT и в начале подбора.

- `200 {"warnings":[...]}` — есть предупреждения.
- `200 {"cleared":true}` — предупреждений нет (или их сбросили последним POST).
- `404` с `"cleared": true` в теле — приложение ещё не присылало предупреждения (вкладка не открыта); трактуйте как «нет данных», не как «всё чисто».

```bash
curl http://localhost:5180/api/warnings
```

Формат Warning:

```json
{
    "code": "base-image-crop",
    "severity": "warn",
    "message": "картинка будет cover-кропнута (аспект 1.78 против 1.33); под аспект картинки — блок 640×360",
    "fix": { "w": 640, "h": 360 }
}
```

- `severity`: `"warn"` — ломает сравнение/эффект, чинить обязательно; `"info"` — заметка.
- `fix` — если есть, готовое исправление полей блока: примените сами через `PUT /api/state` (например, заменить `w`/`h` на значения из fix).
- Коды: `base-image-crop` / `base-image-stretch` / `base-image-contain` (аспект base-картинки против блока > 2%), `ref-transformed` (референс смещён/масштабирован — дифф считает трансформ), `ref-aspect-fill` (референс растягивается), `blur-coverage` (переходы референса вне зоны blur.rect; у radial-таргета покрытие — приближённая оценка, помечено в сообщении), `dup-stops` (стопы ближе 0.5%), `blur-zero-radius` (blur включён с радиусом 0).

### `GET /api/journal` — журнал итераций

Автожурнал подбора: приложение на каждое устоявшееся изменение стейта (агентский PUT или правка юзера, debounce ~700ms) пишет запись — ts, изменённые пути (dot-notation, глубина ≤ 3, максимум 20) и метрики анализа «до» правки; когда следующий анализ посчитан — дозаполняет `after` вторым сообщением. Кольцевой буфер на 200 записей в памяти dev-сервера. Назначение: **агент может читать журнал, чтобы откатиться к удачной итерации** (какие поля крутились и что это дало по метрикам).

```bash
curl http://localhost:5180/api/journal
# {"entries":[{"id":7,"ts":1760000123,"fields":["blur.radius"],"before":{"zoneMatch":87.6,"maxErr":81,"verdict":"..."},"after":{"zoneMatch":91.7,"maxErr":50,"verdict":"..."}}]}
```

- `fields` — только пути (`"blur.radius"`, `"layers.0.gradient"`), значения НЕ пишутся (dataURL картинок в журнал не попадают).
- `before`/`after` — `{zoneMatch, maxErr, verdict}` на момент до/после; `null` — анализа не было (нет референса) или он не успел посчитаться до следующей правки. `after` — метрики первой завершившейся после правок итерации; при слитии правок (несколько изменений до flush записи, напр. A+B в одной записи `{fields:[A,B]}`) семантика — «после первой», т.е. `after` отражает состояние на момент первого анализа, а не всех правок записи.
- `POST /api/__journal` — пишет само приложение (start `{ts, fields, before?}` → ответ `{ok, id}`; finish `{id, after}`); агенту обычно не нужен.
- `DELETE /api/journal` — очистить журнал (`{"ok":true,"cleared":N}`); в dev приложение получает SSE `journal-cleared` и чистит локальное зеркало сразу, на проде — по id-регрессии со следующим своим POST (id пошли заново → зеркало сброшено), чтобы `hint` не детектил «плато радиуса» по удалённым записям.

### `GET /api/events` — SSE-поток обновлений

`text/event-stream`. При подключении сразу присылается текущий кэш (если есть), далее — события `{ "type": "state", "state": {...} }` на каждый `PUT /api/state`, `{ "type": "analysis-request", "target": "..." }`, когда агент запросил `GET /api/analysis?target=...` (приложение пересчитывает анализ под этот таргет), `{ "type": "sweep-request", "id": "...", "req": {...} }` на каждый `POST /api/sweep` (приложение исполняет авто-перебор), `{ "type": "notify", "text": "..." }` на каждый `POST /api/notify` (приложение показывает тост) и `{ "type": "journal-cleared" }` на `DELETE /api/journal` (приложение чистит локальное зеркало журнала — иначе `hint` видел бы удалённые записи; на проде то же ловится по id-регрессии в следующем POST). Heartbeat `: ping` каждые 25 секунд.

```bash
curl -N --max-time 30 http://localhost:5180/api/events
```

Формат событий:

```
data: {"type":"state","state":{ ...BlockState... }}
data: {"type":"analysis-request","target":"blurMask"}
data: {"type":"sweep-request","id":"<uuid>","req":{"field":"blur.radius","from":8,"to":14,"steps":4}}
data: {"type":"notify","text":"поставил стоп на 58.4%"}
data: {"type":"journal-cleared"}
```

### `GET /api/methodology` — методика подгонки v2 (алгоритм из одного места)

Исполняемая процедура F0–F6 — тот же источник, что и текст раздела «Методика подгонки v2» (`src/lib/methodology.ts`). Формат: `{version: 2, phases: [{id: "F0".."F6", title, actions: string[], exit: string}], invariants: string[], text}` — `text` это вся процедура одним блоком, `phases[].exit` содержит условия выхода и запрет возврата (rect после F1, радиус после F2). На проде работает ВСЕГДА (Upstash не нужен). Клиент приложения его не читает — это контракт агентов.

```bash
curl http://localhost:5180/api/methodology
```

### `POST /api/sweep` — авто-перебор значения одной командой

Коридор радиуса (F2) без ручных PUT-циклов: агент оставляет заявку, приложение само прогоняет все значения и отдаёт таблицу метрик.

```bash
curl -X POST http://localhost:5180/api/sweep \
  -H 'Content-Type: application/json' \
  -d '{"field":"blur.radius","from":4,"to":20,"steps":6}'
# {"id":"<uuid>"}
```

- Тело: `{field: "blur.radius", from, to, steps}`; `steps` 2..12 (точек, края включены — linspace). Другие поля пока не поддерживаются (`400`).
- Исполнение (нужно открытое приложение с референсом): заявка доставляется браузеру (dev — SSE `sweep-request`, прод — поле `sweepRequest` поллинга `GET /api/state?since=N`, ≤10 с), приложение для каждого значения транзиентно применяет `blur.radius` (без истории и записей журнала; на сервер транзиенты НЕ синкаются — `GET /api/state` во время sweep честно отдаёт исходный стейт, финальный синк уходит после восстановления), ждёт пересчёта анализа (~600ms) и снимает `{value, zoneMatchPercent, maxError}`; в конце исходный радиус восстанавливается и результат уходит на сервер (`POST /api/__sweep` — агенту не нужен). Таймаут точки — 10 с (анализ не пересчитался, обычно нет референса) → немедленный `aborted`, т.е. худший случай деградации — 10 с, не 12×10; живой sweep ≈ 1.5–2 с × точку (12 точек ≈ 25 с).
- **Юзерский ввод (или чей-либо PUT / переключение таргета) во время sweep = abort**: приложение прекращает перебор, НЕ восстанавливая радиус (не затирает правку), и отдаёт частичную таблицу + `aborted` с причиной. Агенту не стоит делать `PUT /api/state`, пока sweep не завершился.
- Ответ заявки: `{"id": "..."}`. Дальше поллите статус:

```bash
curl 'http://localhost:5180/api/sweep?id=<uuid>'
# {"id":"...","status":"pending"}                          — ещё исполняется
# {"id":"...","status":"done","results":[                  — таблица готова
#   {"value":4,"zoneMatchPercent":91.2,"maxError":81},
#   {"value":7.2,"zoneMatchPercent":95.4,"maxError":52},
#   {"value":10.4,"zoneMatchPercent":98.4,"maxError":19},
#   {"value":13.6,"zoneMatchPercent":97.1,"maxError":33},
#   {"value":16.8,"zoneMatchPercent":90.3,"maxError":77},
#   {"value":20,"zoneMatchPercent":81.6,"maxError":121}]}
# {"id":"...","status":"aborted","results":[...],"aborted":"state/таргет изменён вне sweep ..."}
```

- Статусы: `pending` (заявка ждёт/исполняется — поллите раз в ~1 с, прод ~3 с), `done`, `aborted` (результат мог не приехать вовсе — например, вкладка закрыта: заявка висит `pending` до нового sweep или рестарта dev-сервера; на проде ключ живёт в `lab:s/<id>/sweep/<sweepId>`).
- `404` — id не существует (dev-сервер перезапускался — память потеряна). На проде тот же результат доступен и как `GET /api/sweep/<id>` (path-параметр); статусы сессионные — читаются с тем же заголовком `X-Lab-Session`, что и заявка (чужой сессии тот же id отдаст `404`). GET-статусы (`?id=` и `/<id>`) открыты; `Authorization: Bearer` при заданном `LAB_API_TOKEN` требуют записи — `POST /api/sweep` (заявка и результат), как остальные мутации.

### `POST /api/notify` — сообщение юзеру (тост в его браузере)

Короткий статус от агента: «перебор радиуса завершён: лучший 11.2 (zoneMatch 98.1)», «жду твой прогон». Правило: **сообщения — короткий статус для юзера, не чат** — уведомляйте, когда завершили значимый шаг или всю подгонку; не отправляйте их на каждую итерацию.

```bash
curl -X POST http://localhost:5180/api/notify \
  -H 'Content-Type: application/json' \
  -d '{"text":"поставил стоп на 58.4%, дальше смотришь ты"}'
# {"ok":true,"ts":1760000123}
```

- Тело: `{text}` — строка 1..200 символов (пустая/длинная/не-JSON — `400` с `issues`); `ts` присваивает сервер и возвращает в ответе.
- Сессия — по заголовку `X-Lab-Session` (как у state; без заголовка — `default`): тост увидят вкладки этой сессии.
- Доставка: dev — SSE-событие `{"type":"notify","text":"..."}` (тост сразу, не хранится); прод — поле `notify` в ответе поллинга `GET /api/state?since=` (слот хранит одно последнее сообщение, новое перезаписывает старое, синк/PUT его не стирают). Клиент показывает тост «Агент: \<text\>» только если `ts` новее последнего показанного — повторные доставки того же сообщения молча пропускаются, стирать notify не нужно.
- Мутация: `Authorization: Bearer` при заданном `LAB_API_TOKEN`, как прочие записи. Схема — `NotifySchema` в `src/schema.ts`.

## Методика подгонки v2 (выработана на живой сессии)

Исполняемая процедура: фазы F0–F6 с входом/выходом и запретом возврата к зафиксированным ручкам. Машиночитаемая копия — `GET /api/methodology` (фазы + инварианты + этот же текст одним блоком; единый источник — `src/lib/methodology.ts`, правки только синхронно). Текст процедуры:

```text
ВХОД: base + ref (один момент, одинаковый кроп), полный стейт-файл на диске.
ГЛАВНАЯ МЕТРИКА: zoneMatch(target). РЕШЕНИЯ — по шагам ≥0.5 (дрожжание канвы ±0.3 — шум).
F0 СТАРТ: w/h = аспект кропа; base.image + compare.refImage; export.scale по факту кадров.
  ЦИКЛ: PUT → warnings → чинить ВСЕ warn → пока не cleared. ЗАПРЕЩЕНО мутировать
  пустой стейт (нет base.image/refImage → восстановить из файла).
F1 ГЕОМЕТРИЯ (вне лабы, без PUT-циклов):
  1. сгладить оба кадра: -blur 0x2 (убрать фотошум);
  2. difference → профиль по оси эффекта (строки для низ/верх, колонки для боков);
  3. blur.rect = [onset(>8%max) … 100%]; по умолчанию внутри блока; заход за край —
     только как приём мягкого входа/выхода (легален при stage.isolated: true);
  4. отдельно mean-сдвиг base vs ref по зоне = уровень затемнения Z;
     Z > 2 уровней → заливка будет обязательна (F4).
  ВЫХОД: rect зафиксирован, до F5 НЕ ТРОГАЕТСЯ.
F2 РАДИУС (коридор, не деление от большого): для photo-кадров 1x–2x коридор 8–14px,
  старт с середины (10–12), шаг ±2–3. ВЫХОД: прирост zoneMatch < 0.5 за шаг →
  радиус ЗАФИКСИРОВАН и не меняется ни в одной следующей фазе (плато широкое:
  10/11/12 давали 98.4/98.3/98.2).
F3 МАСКА (форма): предразогрев (0.1@~35% rect) → основной фронт (0.5@~46 → 1@~58)
  → плато до конца зоны. Ручки: позиции стопов + высота пилота. Метрика честна к
  середине маски, но финальную форму утверждает юзер.
F4 ЗАЛИВКА: если Z>2 — обязательна, форма тающая от фронта. Если Z~0 — НЕ добавлять
  «по умолчанию» (роняла 98.4→84.9); после F3 ОДНА проба тонкой тающей (0.15@0→0@100):
  keep если zoneMatch вырос, revert если упал (в сессии дала финальные 98.7 и худшую
  точку 14→10).
F5 ГЕОМЕТРИЧЕСКИЕ ПРИЁМЫ (если plateau < целевого): по одному, keep/revert каждая:
  rect-заход за край (y −20%, h 120%) · двухступенчатая маска · заливка-вспышка.
F6 СТОП: zoneMatch стабилен 2 замера (±0.3 — не прогресс) И verdict без «уровня» И
  остатки только blur (≤3 точек). Отдать baseline юзеру: его руки — финальный
  оптимизатор (2 сессии подряд ручной вариант бил циклический подбор). Перед циклом
  сохранить полный стейт в файл; после каждого PUT сверять base.image/refImage на
  месте; рестарт dev-сервера = пустой кэш → восстановить из файла, пустой стейт
  не мутировать.
ИНВАРИАНТЫ перед КАЖДЫМ PUT: свежий GET; PUT = полный стейт; base.image/refImage
на месте; одна ручка за итерацию; wholesale-резеты запрещены; откат — /api/journal
или локальный state-full.json; решения по Δ≥0.5.
```

Приборы методики: `GET /api/methodology` (алгоритм из одного места), `hint` в ответе анализа («движение к точке») и `POST /api/sweep` (коридор радиуса одной командой) — разделы ниже.

### Анти-бэндинг в экспорте

CodePanel (кнопка «CSS» в хедере) имеет тумблер «Анти-бэндинг» — пост-процесс ТОЛЬКО текста экспорта (CSS/Sass), состояние не меняет: каждый градиент ресэмплится до 12–16 стопов (равномерная сетка + ключевые — локальные экстремумы альфы — точно как есть), не-ключевые стопы получают детерминированный дизеринг ±1–2 по каналам (hash от позиции, без случайности — экспорт стабилен между копированиями).

## Прод (Vercel)

Тот же Agent API поднимается на прод-инстансе Vercel: функции `server/functions/*.ts` (Node runtime, web-standard `Request`/`Response`), стор — **Upstash Redis через REST** (`KV_REST_API_URL` + `KV_REST_API_TOKEN` проставляет интеграция Upstash из Vercel Marketplace; чистый fetch, без npm-пакетов). `api/` — генерируемые самодостаточные бандлы из `server/functions` (роллдаун-сборка `scripts/build-functions.mjs` на шаге `npm run build`; Vercel сканирует `api/` после buildCommand — источники там не живут, внешних рантайм-импортов у бандлов нет). Агент работает **тем же циклом** (PUT → warnings → analysis → journal → пресеты), curl-примеры из этого документа годятся после замены `http://localhost:5180` → `https://<project>.vercel.app`. Отличия:

- **Нет SSE.** `/api/events` на проде не существует; браузер получает агентские PUT поллингом версии: `GET /api/state?since=N` раз в ~10 с (в скрытой вкладке поллинг стоит; при сбоях/квоте — экспоненциальный бэкофф до 60 с, сброс при первом живом ответе). Живой отклик PUT — ≤10 с; контрольная сверка GET после PUT — через ~12 с.
- **Контракт версий** (эхо без броадкаста):
    - любая запись стейта — `PUT /api/state` (агент) или `POST /api/sync` (браузер, прод-аналог `__sync`) — инкрементит счётчик `lab:s/<id>/ver` и пишет слот `lab:s/<id> = {version, state, analysisReq?, sweepReq?, notify?, name, updatedAt}` — версия, стейт и заявки агента (анализ таргета / авто-перебор) + его последнее сообщение юзеру **одним ключом**, чтобы полл-тик стоил ровно 1 команду Upstash;
    - `GET /api/state?since=N` → `200 {version, state, analysisRequest?, sweepRequest?, notify?}` при `version > N`, иначе `200 {version: N, unchanged: true, analysisRequest?, sweepRequest?, notify?}` (**не 404** — поллинг дешёвый); без `?since` — голый `BlockState`, как в dev; заявки отдаются в обоих ветках, пока не закрыты (анализ — `POST /api/analysis`, sweep — `POST /api/__sweep`), `notify` — пока не перезаписан следующим `POST /api/notify`;
    - `POST /api/sync` (тело `{state}` или голый стейт) отвечает `{ok:true, version}` — браузер запоминает «моя версия»; `PUT /api/state` отвечает `{ok:true, version}`;
    - **почему нет петли**: `sync` ничего не броадкастит; браузер не запрашивает обратно версию, которую сам записал (свой синк подтянул `since`), а чужую версию применяет и не отсылает обратно (identity-чек в подписке стора — тот же механизм, что в dev с SSE). Потерянный ответ синка страховён контент-сверкой: если приехал стейт байт-в-байт наш (последний отправленный или текущий локальный), применяется только версия, контент не трогается — несинкнутая юзерская правка не откатывается (гарантия практическая: при потере ответа синка + юзерской правке в окне до полл-чтения (~1с) правка B может быть откачена — редкая комбинация, восстановима повторной правкой или Ctrl+Z). Юзерские правки поверх применённого — обычный last-writer-wins.
- **Запрос анализа таргета** (`GET /api/analysis?target=X` при кэше другого таргета): промах — это **запись** (read-modify-write `analysisReq` в `lab:s/<id>`, с сохранением `sweepReq`), поэтому при заданном `LAB_API_TOKEN` он требует `Authorization: Bearer`, как остальные агентские мутации (анти-спам заявок от анонимных клиентов); попадание в кэш и чтение без `?target` открыты. Заявку браузер забирает тем же поллом (поле `analysisRequest`), переключает таргет, пересчитывает и присылает анализ `POST /api/analysis`, стирая заявку. Итог для агента: `404 {requested}` → повторять GET раз в ~5 с, ответ придёт в течение ~12 с.
- **Авто-перебор и методика на проде**: `POST /api/sweep` пишет заявку в `sweepReq` того же слота `lab:s/<id>` (полл-тик остаётся 1 командой; транзиентные значения на сервер не синкаются — лишних версий/команд sweep не создаёт) плюс `lab:s/<id>/sweep/<sweepId> = {req, status, results?}` — id сессии в ключе, чужой sweep по id не читается; браузер подхватывает заявку поллом (≤10 с), исполняет (~1.5–2 с на точку; таймаут точки 10 с → `aborted`, без референса — это первые же 10 с) и шлёт результат `POST /api/__sweep` (rewrite → `POST /api/sweep`, тело `{id, results?, aborted?}`), который обновляет ключ результата и стирает заявку. Статус: `GET /api/sweep?id=` или `GET /api/sweep/<id>` — поллите раз в ~3 с, исполнение всей таблицы до ~30 с. `GET /api/methodology` Upstash не касается — отвечает всегда, даже без env.
- **Авторизация (опционально)**: env `LAB_API_TOKEN` — все мутации (PUT state, POST sync/analysis/warnings/journal, DELETE journal, PUT/DELETE presets, промах `GET ?target=`) требуют `Authorization: Bearer <token>`; без заголовка — `401`, с неверным — `403`; чтение открыто. Браузер шлёт токен из `VITE_LAB_TOKEN` (тот же токен; **виден в бандле** — годится только для закрытых инстансов, не для публичных URL; в dev он лишь добавляет заголовок — middleware его не проверяет, безвредно).
- **Пути**: канонические имена на проде — `/api/sync`, `/api/analysis`, `/api/warnings`, `/api/journal`; dev-имена `/api/__sync` и пр. работают через rewrites в `vercel.json` (совместимость curl-цикла; `__sweep` → `/api/sweep`). `/api/state`, `/api/warnings`, `/api/analysis`, `/api/journal`, `/api/schema`, `/api/methodology`, `/api/sweep` (+ `?id=` и `/<id>`), `/api/notify`, `/api/presets`, `/api/presets/:name`, `/api/sessions`, `/api/sessions/:id` — те же имена, что в dev (sessions — только прод, см. «Сессии» ниже).
- **Пресеты и журнал** живут в Upstash, а не в файловой системе: `lab:preset:<name>` + индекс `lab:presets`, `lab:journal` (cap 200). Это НЕ локальная папка `presets/` — у прода своё множество пресетов. UI PresetDrawer на проде файловые пресеты не показывает (осознанно: флаг `devApiAvailable` ставится только в dev) — агент работает с ними напрямую через `GET/PUT/DELETE /api/presets/:name`. Форматы записей — те же.
- **Без env Upstash** любая функция отвечает `503 {"error":"prod API не настроен: ..."}` — приложение при этом живёт как обычная статика (поллинг не поднимается).

### Сессии (мульти-агент)

Прод — мульти-сессионный: каждый агент/юзер работает в своём слоте доски, а не в одной общей. Сессия задаётся заголовком **`X-Lab-Session: <id>`**; без заголовка — сессия `default`. id — `[a-zA-Z0-9_-]`, 1..64 символа; невалидный — `400`.

- Заголовок принимают и срезают по нему данные: `/api/state` (GET/PUT), `/api/sync`, `/api/analysis` (GET/POST), `/api/warnings` (GET/POST), `/api/sweep` (заявка/результат/статус `?id=` и `/<id>`), `/api/notify` (запись). Журнал `/api/journal` — общая лента, заголовок принимается, но лента одна. Пресеты, `/api/schema`, `/api/methodology` — глобальны (без сессии).
- **Ленивое создание**: обращение к несуществующей сессии (включая GET) создаёт слот с пустым стейтом (версия 0) и строкой в индексе. Единственное исключение — `DELETE /api/sessions/<id>` (404). Создание слотов неавторизованными GET-ами возможно: без `LAB_API_TOKEN` ключи `lab:s/*` плодятся от любого запроса с новым заголовком (индекс держит cap 50) — для приватных инстансов ставьте токен.
- **Изоляция**: стейт/версии/заявки (`analysisReq`/`sweepReq`), warnings, analysis-кэш и sweep-результаты живут в ключах слота `lab:s/<id>*` (таблица ключей ниже); чужой sweep по тому же id не читается — id сессии зашит в ключ результата. Счётчики версий у сессий независимы.

Управление сессиями:

- `GET /api/sessions` → `{sessions: [{id, name, updatedAt}]}`, новые сверху. Чтение открыто. Индекс cap 50: при переполнении выкидываются самые неактивные (по `updatedAt`); слот при этом остаётся и пересоздаёт строку при следующей записи.
- `PUT /api/sessions/<id>` тело `{name}` (строка 1..64) — создать (пустой слот) или переименовать. Под `Authorization: Bearer` при заданном `LAB_API_TOKEN`, как прочие мутации. Ответ `{ok, id, name}`.
- `DELETE /api/sessions/<id>` — удалить слот: стейт, счётчик версий, warnings, analysis и заявки (analysisReq/sweepReq жили в слоте). Единственная операция, требующая существования сессии (`404`). Тоже под Bearer. Орфанные ключи sweep-результатов не перечислимы без SCAN — остаются (не читаются без uuid). `default` удалять можно — слот пересоздастся лениво.

**Миграция односессионной эпохи**: при первом обращении к сессии `default`, если её слота ещё нет, а legacy-ключи `lab:state`/`lab:statever`/`lab:warnings`/`lab:analysis` существуют — они переносятся в слот `default` (RMW, не транзакционно), legacy-ключи удаляются; счётчик версий продолжается с прежнего значения. Старые деплои обновляются без потерь.

**Клиент приложения**: сессия хранится в `sessionStorage['lab.session']` — «мой агент — моё окно»: два окна = две сессии. Все прод-вызовы браузера (sync/analysis/warnings/journal/sweep-результат и поллинг `?since=`) несут тот же заголовок; значение читается в момент запроса. Селектор в хедере (только прод): «Сессия: <id>» → поповер с полем id («Открыть/создать»), списком живых сессий и кнопкой «Инструкция агенту» (копирует бриф с origin + текущей сессией + минимальным циклом). Смена сессии перезапускает поллинг с нулевой версии (версия/эхо-сброс), вид (зум/пан) не трогается.

**Join-ссылки агенту**: `https://<project>.vercel.app/?join=<id>` — открывает вкладку юзера сразу в сессии агента: значение уходит в `sessionStorage` до первого синка, параметр вычищается из URL (`replaceState`); `#s=`-стейт из той же ссылки применяется в эту сессию.

**dev всегда `default`**: dev-сервер :5180 однопользовательский — селектор в хедере скрыт, браузер заголовок не шлёт (middleware его игнорирует), сессийного слоттинга в dev нет.

Ключи Upstash (слоты сессий — `lab:s/<id>*`, см. «Сессии»): `lab:s/<id>` (JSON `{version, state, analysisReq?, sweepReq?, notify?, name, updatedAt}` — стейт-слот с мета-сессии одним ключом), `lab:s/<id>/ver` (счётчик версий слота), `lab:s/<id>/warnings`, `lab:s/<id>/analysis` (JSON с `target`), `lab:s/<id>/sweep/<sweepId>` (JSON `{req, status, results?, aborted?}`), `lab:sessions` (индекс `[{id, name, updatedAt}]`, cap 50), `lab:journal` (общая лента, JSON-массив, cap 200), `lab:presets` + `lab:preset:<name>` (глобальны). Legacy-ключи односессионной эпохи `lab:state`/`lab:statever`/`lab:warnings`/`lab:analysis` мигрируют в слот `default` при первом обращении (разово, RMW).

### Квота и честные ограничения

- **Команды/день**: полл-тик = ровно 1 команда (`get lab:s/<id>` — слот читается одним ключом); активная вкладка 8 ч = 28 800 с / 10 с ≈ **2 880 команд**. Одна правка юзера ≈ 13 команд (sync 5 — включая обновление строки индекса сессий, warnings 2, journal 2–4, analysis 4) — даже сотня правок за день держит итог в районе ~5–6k, в пределах free-тарифа Upstash (10k команд/день). При исчерпании квоты Upstash отвечает 429 → прод-функция отдаёт 502 → браузер уходит в бэкофф до 60 с и **сам восстанавливается** после сброса суточной квоты (сброс счётчика неудач — на первом живом ответе).
- **Не транзакционно (last-writer-wins)**: `INCR`+`SET` стейта, read-modify-write заявки (`POST /api/analysis` со стираемой `analysisReq` может перетереть параллельный sync), журнала и индексов (пресетов, сессий) не атомарны — параллельные записи могут перетереть друг друга. Конфликты живут внутри одной сессии (максимум «агент + один браузер»); гонки на индексе `lab:sessions` самовосстанавливаются — потерянная строка пересоздаётся следующей записью слота. Рассинхрон самовосстанавливается следующим PUT/синком; агенту — свежий GET перед каждым PUT, как обычно. Журнал: параллельные POST могут потерять последнюю запись — цена простого стора, для инструмента подбора приемлемо.

### Setup-чеклист

1. Импортируйте репозиторий в Vercel (framework Vite; `vercel.json` уже задаёт `npm run build` → `dist`; функции из `api/` и статика `dist/` не конфликтуют — у Vite нет `dist/api`).
2. Vercel → Storage → Marketplace → **Upstash Redis** (free) → подключите к проекту — в env появятся `KV_REST_API_URL`/`KV_REST_API_TOKEN`.
3. (опционально) закрыть мутации: добавьте env `LAB_API_TOKEN` (сервер) и `VITE_LAB_TOKEN` с тем же значением (клиент).
4. Deploy → проверка `curl https://<project>.vercel.app/api/schema` — JSON Schema; дальше агент стучится в `https://<project>.vercel.app/api/...` тем же циклом (включая «Методику подгонки v2» ниже и `GET /api/methodology`, который работает и без Upstash).

Замечания:

- `pos` стопов может выходить за `0..100` (напр. `-13.94` — приём из onsport select).
- `layers[].rect` — область слоя `{ x, y, w, h }` в % ОТ блока, та же семантика, что `blur.rect`: `x`/`y` могут выходить за `0..100` (области затекания), `w`/`h` >= 1, дефолт `{0,0,100,100}` (zod-`.default()` — старые стейты без поля валидны). Экспорт-семантика: полный rect → `inset: 0`, неполный → 4 декларации `left/top/width/height` в % ОТДЕЛЬНЫМИ строками (в indented Sass запятые превратили бы их в мусорный список). Геометрия градиента слоя (угол оси linear, центр/радиусы radial) считается в системе rect — CSS считает градиент от border-box элемента; ось анализа `layer:N` тоже (`axisSpace: "layer.rect"`), `zone` = rect слоя. В UI у активного rect-таргета (слой/blur/underlay) есть хэндлы на канвасе: drag внутри контура — перенос (при ЛЮБОМ rect, включая полный 100%), углы — ресайз (Shift — пропорциональный), значения без clamp, над контуром чип-подпись таргета. Активный таргет главнее блока: пока rect-таргет активен, drag/углы внутри его контура двигают таргет, а не блок — блок переносится через Alt+drag, ресайзится через Alt+углы или полями X/Y/W/H инспектора; вне контура (частичный rect) блок двигается как обычно, без Alt.
- `blur` — это ОДИН псевдоэлемент ОГРАНИЧЕННОЙ области внутри блока, несущий ВМЕСТЕ градиентный фон (`blur.gradient`) + `backdrop-filter: blur()` + маску (`blur.mask`). Не раскладывай на разные слои. `blur.rect` — `{ x, y, w, h }` в % ОТ блока; `x`/`y` могут выходить за `0..100` (области затекания часто заходят за край), `w`/`h` >= 1; дефолт `{0,0,100,100}`. В экспорте это один класс `.gradient-block__blur` с `left/top/width/height` в %. Легаси `background` (плоский rgba-цвет) используется только когда `gradient === null` (`gradient ?? background`); в инспекторе выбор подложки «Нет | Цвет | Градиент». Поля `gradient`/`rect`/`underlay` имеют zod-дефолты — старые стейты без них остаются валидными.
- `blur.underlay` — подложка затемнения ПОД blur-элементом (порядок слоёв: base → layers → underlay → blur; в проекте это конструкция «::before затемнение + ::after blur», в экспорте лаборатории — класс `.gradient-block__blur-underlay` ПОД `.gradient-block__blur`). Без маски и блюра, со своей `rect` (`{x,y,w,h}` в % от блока) и заливкой `gradient ?? color` (цвет — rgba-строка). Дефолт выключен; включается, когда чистого `blur.gradient` не хватает — для плотных затемнений под каруселями.
- `compare.mode`: `"off" | "opacity" | "difference" | "split" | "analysis"`. `split` — A/B-разделитель блока, ось задаётся `splitDir`: `"vertical"` (линия двигается влево/вправо, клип `inset(0 0 0 splitPos%)`) или `"horizontal"` (вниз/вверх, `inset(splitPos% 0 0 0)`). `analysis` — heat-карта попиксельных расхождений (чёрный = совпадение в пределах `tolerance`); метрики см. `GET /api/analysis`. `splitDir`/`tolerance` имеют дефолты (`"vertical"`/`10`).
- `base.kind`: `"color" | "gradient" | "image"`; при `"gradient"` фон блока — `background: <gradient>` из `base.gradient` (поле обязательно при любом kind; в Sass-экспорте выносится в `$g-base`). При `"image"` тот же `base.gradient` — **вуаль поверх картинки**: превью — отдельный слой над `<img>`, экспорт — multiple backgrounds `background-image: <gradient>, url("...")` с градиентом ПЕРВЫМ слоем (в Sass — переменная `$g-veil`); alpha-профиль решает видимость — все α=0 дают невидимую (но корректную) вуаль, дефолт — чёрная наполовину с растворением к низу. Дифф-анализ вуаль учитывает.
- `radial`-градиент: `{ "type": "radial", "cx", "cy", "shape": "circle|ellipse", "size": "closest-side|closest-corner|farthest-side|farthest-corner|explicit", "rx", "ry", "repeating", "stops" }`; при `size: "explicit"` рендерится как `ellipse Rx% Ry% at Cx% Cy%`.
- `stage.bg`: `"checker" | "solid" | "image"` — три режима фона стейджа. При `"image"` под блоком рендерится `stage.image` (dataURL) со смещением `x`/`y` (px) и масштабом `scale` (%) от натурального размера — чтобы честно проверять backdrop-blur и blend-режимы блока поверх реального контента (скриншота страницы/слайдера). Поля `image`/`x`/`y`/`scale`/`isolated` имеют zod-дефолты (`null`/`0`/`0`/`100`/`true`) — старые стейты без них остаются валидными.
- `stage.isolated` (default `true`): блок — backdrop root (`isolation: isolate` в превью и экспорте). В реальном браузере родитель с isolation клипает сэмпл блюра: backdrop-filter блюрит только содержимое блока. Канва анализа при `true` за краем блока сэмплирует копии краевых пикселей (clamp-to-edge вместо прозрачности) — got у кромки честный, edge-residual исчезает при rect до края. Выключайте, чтобы в превью blur блюрил картинку стейджа за блоком.
- `export`: пересчёт величин кропа лаборатории в величины макета — `{ "scale": 2, "remBase": 10, "designWidth": 1440 }`, все поля с дефолтами (старые стейты валидны). Формула пересчёта: `pxcss = pct / 100 · blockW / scale` (blockW — ширина блока лаборатории, pct — % кропа); `rem = pxcss / remBase`; `% макета = pxcss / designWidth · 100`. Пример: 24% кропа при blockW 1050, scale 2 → 126px = 12.6rem = 8.75% макета. В UI те же подсказки — панель «Пересчёт в макет» в секции «Блок» (границы/ширина blur.rect, радиус, высота underlay). В API подсказки не отдаются — агент считает сам по этим формулам.
- `compare.refImage` / `base.image` / `stage.image` — dataURL; в URL-share и localStorage их лучше не раздувать.
